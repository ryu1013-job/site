# PRD: 介護のげんかん

**Version:** 0.2  
**Status:** Draft  
**Platform:** モバイルWeb（PWA可）  
**One-liner:** 介護の節目ごとに「次にやること」を出し、家族と専門職で共有できる1枚を育てるWeb。

---

## 0. v0.1 からの変更（ブラッシュアップ要旨）

v0.1 は「問診 → 次の一手」の情報プロダクトだった。以下3点を修正する。

| # | v0.1 の弱点 | v0.2 の方針 |
|---|---|---|
| 1 | 汎用の助言は LLM に無料で代替される | **情報ではなく状態と成果物**を持つプロダクトにする |
| 2 | 「玄関」= 一回性。介護は数年続くのに戻る理由がない | **節目トリガー**を P0 に格上げし、繰り返し通う場所にする |
| 3 | 全ステージを薄く狙い、チャネルが分散 | **退院前後にウェッジを絞る**（MSW経由の配布を先に取る） |

結果、コアオブジェクトは「結果画面」ではなく **引き継ぎシート** になる。

---

## 1. Problem

初めて在宅介護に直面した家族は、情報は多くても「自分は今なにをすればいいか」が分からず止まる。  
そして動き出した後も、節目ごとに同じ迷子を繰り返す。

- 介護保険は申請主義で、動かないと何も始まらない
- 窓口が包括・市役所・病院MSW・ケアマネに分散している
- 記事や自治体HPは静的で、自分のケースに落ちない
- 更新・住宅改修の事前申請など、期限付き手続きを落としやすい
- 専門職に会うたび、同じ説明を最初からやり直す

---

## 2. Why not ChatGPT

汎用LLMに「親が退院する、何をすればいい」と聞けば、一般的な手順はもう返ってくる。  
**一般論の提供では勝負にならない。** 勝てる差は3つだけ。

| 差 | 中身 | LLMが弱い理由 |
|---|---|---|
| **状態** | どこまで進んだかを覚えていて、次に来るものを先に言う | 会話は続かない、期限を能動的に通知しない |
| **土地** | 実在する包括の連絡先・自治体差を、確認済みで出す | 幻覚リスクが最も高い領域 |
| **成果物** | 専門職に渡せる／家族で共有できる1枚 | チャットログは渡せない |

**設計判断:** 「うまく答える」ことに投資しない。**覚える・追う・渡す**に投資する。

---

## 3. Core Object: 引き継ぎシート

プロダクトの中心はページ遷移ではなく、育っていく1枚。

**中身**
- 本人の基本（年齢帯・住まい・認定有無・要介護度・有効期限）
- 困りごと（家族の言葉で言語化されたもの）
- 経過（いつ何を済ませたか）
- 次にやること（期限つき）
- 家族の体制・分担
- かかりつけ／担当ケアマネ等の関係者

**ライフサイクル**
1. 問診で生成される
2. 節目（退院・更新・状態変化）で更新を促される
3. 包括・ケアマネ・MSW との面談前に提示される
4. 家族間で共有され、同じ説明の反復を減らす

**なぜこれが主役か**
- 何度も戻る理由になる（リテンション）
- 専門職に渡ることで配布チャネルになる（グロース）
- 蓄積された状態は他サービスに移植しづらい（ディフェンス）

---

## 4. Wedge: 退院前後

全ステージを薄く狙わず、**退院**に集中する。

| 理由 | 内容 |
|---|---|
| 緊急性 | 期日が決まっており、先送りできない |
| トリガーの明確さ | 「退院日」という単一入力で逆算できる |
| チャネル | 病院MSW・退院支援部門が実在する配布経路 |
| 検索需要 | 「親 退院 介護 何から」は最も切実な検索 |
| 波及 | ここで認定申請まで進めば、その後の節目もこのシートに乗る |

ウェッジで勝ってから、物忘れ初動・更新期限・区分変更へ横展開する。

---

## 5. Goals / Non-goals

### Goals
- **30秒**で最初の一手に到達する（全問回答を待たせない）
- 初動家族が **48時間以内**に最初の連絡（包括／窓口／MSW）まで進む
- 面談前に **引き継ぎシート**を持って専門職に会える
- **節目（更新・退院・状態変化）で戻ってくる**
- 連絡先探しを Google に逃がさず、サイト内で完結させる

### Non-goals（v1）
- 要介護度の推定・診断
- ケアプランの自動作成
- 単一事業所の押し売りレコメンド
- 日常介護記録の代替
- 汎用チャットボットとしての何でも回答
- ネイティブアプリ必須

---

## 6. Users

| 優先 | セグメント | ニーズ |
|---|---|---|
| P0 | 退院を控えた親を持つ子世代 | 期日までに何を済ませるか |
| P1 | 遠距離・共働きケアギバー | 台本・共有・電話で進めたい |
| P2 | 病院MSW・退院支援 | 準備できた家族と話したい／説明負荷を下げたい |
| P3 | ケアマネ／包括 | 初回面談の聴取漏れを減らしたい |
| P4 | 企業人事 | 介護離職防止・周知義務の実ツール |

---

## 7. Product Principles

1. **診断ではなく案内**（要介護度を当てない）
2. **30秒で最初の価値**（段階的に深める）
3. **次の一手は最大 3 件**
4. **答えるより、覚えて追う**
5. **ケアマネの前工程**であり代替ではない
6. **サイト内完結**（検索エンジンへ逃がさない）
7. **サービスはまず種別**、事業所はデータ後続

---

## 8. User Journey (v1)

### 初回（段階的問診）

| 段階 | 質問 | 返すもの | 所要 |
|---|---|---|---|
| **L1** | きっかけ／認定有無／市区町村 | 暫定の一手 1件＋相談先 | 約30秒 |
| **L2** | 距離・ケアマネ・困りごと・緊急度・退院日 | 一手 最大3件＋電話台本 | ＋約1分 |
| **L3**（任意） | 詳細・家族体制・服薬など | 引き継ぎシート生成・共有・種別レコメンド | ＋数分 |

L1 で必ず何かを返す。全問回答を前提にしない。

### 実行
`tel:` で発信 → 「連絡した」チェック → 次アクション解放 → シートに経過が記録される

### 再訪（節目）
トリガー検知 → 「変わったことはありますか」1問 → シート更新 → 次の一手

---

## 9. 節目・期限エンジン（P0）

| トリガー | 検知方法 | 出すもの |
|---|---|---|
| 認定有効期限 60日前 | 入力された期限 | 更新申請の手配（ケアマネ代行 or 窓口） |
| 退院日の接近 | 入力された退院日 | 退院前チェック、暫定ケアプランの確認 |
| 未完了アクションの滞留 | 進捗 | やさしいリマインドと分割提案 |
| 状態変化の申告 | 再訪時の1問 | 区分変更・サービス追加の相談 |
| 住宅改修・用具の検討 | ニーズ入力 | **事前申請が必要**の注意を先出し |

通知手段は v1 ではメール／ブラウザ通知。PWA 通知は後続。

## 10. Functional Requirements

### 10.1 段階的問診
- L1: きっかけ、認定有無、市区町村（3問）
- L2: 距離、住まい、ケアマネ有無、包括連絡有無、困りごと、緊急度、退院日
- L3: 年齢帯、要介護度、有効期限、家族体制、関係者

### 10.2 エンジン
- Stage 判定（S0–S6）
- Action 発火（最大3、優先度つき）
- ニーズ → サービス種別マッピング（**認定後に重み付けを上げる**）
- 節目トリガー評価
- Guard: 断定禁止、確認先併記、鮮度表示

### 10.3 引き継ぎシート
- 問診結果から自動生成、後から編集可
- 印刷／PDF／画面提示（面談で見せる前提のレイアウト）
- 家族共有リンク（閲覧＋進捗、編集権限は分離）
- 更新履歴

### 10.4 連絡先データ
- 厚労省オープンデータ等を定期取込
- v1: 地域包括支援センター＋市の介護窓口を優先
- 表示: 名称・電話・住所・**データ時点**
- 欠落時: 断定番号を出さずフォールバック案内

### 10.5 サービスレコメンド
- サービス種別＋理由＋注意（限度額・事前申請・ケアマネ調整）
- **認定前は控えめ、認定後・ケアマネ面談前に前面化**
- v1.1+: 同市区町村の事業所一覧（情報公表データ）
- 単一推し・非開示アフィリエイト禁止

## 11. Data Model (概要)

- `Municipality`（コード・名称）
- `Center`（包括等: phone, address, source, sourced_at）
- `CareSheet`（本人状況・困りごと・関係者・共有トークン）
- `SheetEvent`（経過・完了アクション・更新履歴）
- `Deadline`（種別・期日・通知状態）
- `ActionTemplate` / ルール
- `ServiceType` / ニーズ対応表

連絡先は手メンテ電話帳にしない。公式ミラー＋鮮度メタデータを必須とする。

## 12. Success Metrics

| 層 | 指標 | 初期目標（目安） |
|---|---|---|
| Activation | L1 到達（最初の一手を見た） | ≥ 80% |
| Activation | L2 完了 | ≥ 55% |
| Action | 48h 以内の初動実行 | ≥ 40% |
| Artifact | 引き継ぎシート生成 | ≥ 35% |
| Artifact | 家族共有 or 専門職提示 | ≥ 20% |
| Retention | 30日以内の再訪 | ≥ 25% |
| Retention | 節目トリガーからの復帰 | ≥ 30% |

事業KPI（後続）: 病院・企業パイロット数、専門職からの配布経由流入。

**North Star:** 節目をまたいで使われた引き継ぎシートの数。

## 13. Monetization

家族向け入口は無料。収益は供給側から。

| 柱 | 顧客 | 売るもの |
|---|---|---|
| 主 | 企業（両立支援・福利厚生） | 従業員向け利用＋匿名レポート。**「周知した数」ではなく「初動に到達した数」**を出せることが差別化 |
| 主 | 病院（退院支援部門） | 家族の準備サマリー。退院支援の説明負荷軽減。ウェッジと同じ導線 |
| 副 | 居宅・包括 | 初回面談前の引き継ぎシート受け取り |
| 補助 | 保険外サービス | 審査付き・複数提示・開示つき送客のみ |
| 小 | 家族プレミアム | 共有・期限・専門家チャット |

---

## 14. Risks & Mitigations

| リスク | 対策 |
|---|---|
| **汎用LLMに食われる** | 一般論で勝負しない。状態・土地・成果物に投資 |
| **一回性で終わる** | 節目エンジンをP0化。North Star を再訪ベースに |
| 「包括に無料で聞ける」 | 電話**前**の準備と、電話**後**の継続を担う位置に置く |
| 制度・番号の誤り | ルール優先、鮮度表示、確認先必須、報告導線 |
| ケアマネ・専門職の反発 | 前工程であることを明記。シートは専門職の利益にもする |
| 自治体データ欠損 | 包括に絞る、カバレッジ開示、フォールバック |
| 段階問診の作り込み過多 | L1 は3問固定。分岐は L2 以降のみ |

---

## 15. Milestones

1. **検証:** 退院ケースに絞った手動結果返却＋シート手書き
2. **v1 Web:** 段階問診 → 一手 → 引き継ぎシート生成・共有
3. **節目:** 期限エンジンと再訪導線
4. **データ:** 包括連絡先のサイト内表示
5. **B2B:** 病院（退院支援）→ 企業の順でパイロット
6. **拡張:** 事業所一覧、PWA通知、横展開（物忘れ・更新）
